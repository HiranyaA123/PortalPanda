## Executive verdict

The engineering baseline is genuinely good. There is no horizontal overflow on any route at 390px, the CSS is clean (0 unused classes of 255), the build is fast and small (76 KB gzipped JS, 13 KB gzipped CSS), accessible names are present on every interactive element, the ARIA tab pattern is properly implemented, and the previous audit's worst offences — auto-rotating carousels, `CountUp` lying to screen readers, inconsistent CTA language — have all actually been fixed. That is real progress and it should not be undone.

The problems now fall into three distinct buckets, and they are not the same kind of problem:

1. **Two silent regressions.** An entire animation system is dead code, and the CSS-pruning script is what killed it. This is invisible in review because nothing errors — it just quietly does nothing on every page.
2. **A structural SEO/social defect.** The site is a client-rendered SPA with no pre-rendering, so every route ships the *homepage's* title, description and canonical URL in its HTML. Anything that doesn't run JavaScript — every social platform's link unfurler, most non-Google crawlers — sees seven pages that all claim to be the homepage.
3. **A commercial evidence gap that the rebuild did not close.** The site is now well-built and well-written, but it still cannot answer the questions a venue owner asks before wiring their Friday-night service to an unfamiliar supplier. There is no customer testimonial, no ABN, no named human, no price anchor, no support terms, and no answer to "what happens when it breaks."

Fixing bucket 1 is a morning. Bucket 2 is a day. Bucket 3 is the one that actually decides whether the site converts, and it is not an engineering task.

## P0 — Critical

### 1. The entire scroll-reveal system is dead code — ✅ FIXED

`Reveal.jsx` is used on Home, Platform, Pricing, Live and Contact. It mounts an `IntersectionObserver` per instance, holds React state, and toggles `is-visible`. **There are no `.reveal` or `.is-visible` rules in the stylesheet.** All that remains at [src/index.css:1298](src/index.css#L1298) is the comment header:

```css
/* ============================================================
   Scroll reveal
   ============================================================ */
/* (nothing — the rules were deleted) */
```

Verified live on `/pricing`:

```
revealCount: 17
computedOpacity: "1"
computedTransform: "none"
cssRulesTargetingReveal: []      ← no stylesheet rule matches .reveal or .is-visible
```

So 17 `IntersectionObserver`s on one route, plus a React re-render each, produce **zero visual effect**. Every page pays the cost and gets nothing.

**Cause:** almost certainly `npm run audit:css:fix`. `Reveal.jsx` composes its class with a template literal — `` `reveal ${visible ? 'is-visible' : ''}` `` — and the script's Babel-based scanner does not resolve that to the literal strings `reveal` and `is-visible`, so it classified both as unused and deleted them. The README's own warning ("Always run the production build and responsive browser checks after using `--fix`") is exactly the check that would have caught this, and it did not happen.

**Fix:** restore the rules *and* fix the tool that ate them.

```css
.reveal { opacity: 0; transform: translateY(12px); transition: opacity .5s ease, transform .5s ease; }
.reveal.is-visible { opacity: 1; transform: none; }
@media (prefers-reduced-motion: reduce) { .reveal { opacity: 1; transform: none; } }
```

Then teach `scripts/audit-css-usage.mjs` to treat template-literal quasis as class sources, and add a permanent-keep allowlist. Until it is fixed, `audit:css:fix` is a footgun that will silently delete rules again. **Do not run it again in its current state.**

> **Related risk:** this same blind spot means any *other* conditionally-applied class may already have been deleted. `is-active`, `is-selected`, `is-thread-reached`, `is-inactive`, `is-wip`, `nav--open`, `header--scrolled` are all applied via template literals or conditionals. Audit those rules individually before trusting the "0 unreferenced" result.

**✅ Resolution.** The root cause was narrower and more specific than "template literals aren't scanned" — the walker *does* handle `TemplateLiteral`, but `Reveal.jsx` wrote `` `reveal …`.trim() ``, and `collectExpression`'s `CallExpression` branch only visited `node.arguments`. For a method call the template literal is `callee.object`, which was never traversed, so every class named only inside it looked unused.

Three changes:
1. `collectExpression` now visits `node.callee.object` for member calls ([scripts/audit-css-usage.mjs](scripts/audit-css-usage.mjs)).
2. A `KEEP` set pins the runtime-toggled state classes (`reveal`, `is-visible`, `is-active`, `is-selected`, `is-wip`, `is-thread-reached`, `menu-open`, `nav--open`, `header--scrolled`, `is-inactive`) so `--fix` can never remove them even if the walker regresses again.
3. `--fix` now prints every class it is about to delete. The silent deletion is what let this ship unnoticed.

The `.reveal` / `.reveal.is-visible` rules are restored, with a `prefers-reduced-motion` branch that forces `opacity: 1` so content stays readable if the observer never fires. `Reveal.jsx` now builds its class with `.filter(Boolean).join(' ')`, which also fixes finding 27.

Verified by regression probe — a class referenced *only* inside a `.trim()`ed template literal:

```
OLD logic (pre-fix):  Classes unreferenced by current source: 1  → zz-probe-only   (would be deleted)
NEW logic (fixed):    Classes unreferenced by current source: 0                     (correctly kept)
```

And live in the browser, caught mid-transition while scrolling: `class="reveal is-visible cp-outcome"`, `opacity: 0.44`, `transform: translateY(6.66px)`. The animation runs again. Class count went 255 → 257.

### 2. Every route serves the homepage's title, description and canonical — ✅ FIXED

The site is client-rendered with no pre-render or SSR step. Confirmed by fetching a subroute directly:

```
$ curl -s http://localhost:5173/platform | grep -o '<title>[^<]*</title>'
<title>Restaurant Website, CRM &amp; Venue Software | CentralPass</title>   ← homepage title
```

The same response contains `<link rel="canonical" href="https://www.centralpass.au/">` and the homepage `og:title` / `og:description` / `og:url`. `seo.js` corrects all of this — but only *after* React mounts and `applySeo()` runs.

Two distinct consequences:

**a) Social sharing is broken on all 7 non-home routes.** Facebook, LinkedIn, WhatsApp, Slack, iMessage, X and Discord unfurl links with crawlers that **do not execute JavaScript**. Paste `centralpass.au/live` — your portfolio, your single best sales asset — into a DM to a prospective venue and it renders as "Restaurant Website, CRM & Venue Software | CentralPass" with the generic homepage description. Every page you would ever want to share is misrepresented. For a business whose pipeline is door-knocking and follow-up messages, this directly damages the sales motion.

**b) Every page canonicalises to `/`.** A `rel=canonical` pointing at the homepage is an explicit instruction to search engines to *not* index that URL and to consolidate it into `/`. Googlebot renders JS and will usually see the corrected tag, but this is a race between the raw HTML and the rendered DOM, and non-Google crawlers (Bing, AI crawlers, ahrefs, LinkedIn) largely won't win it. You are shipping a de-indexing instruction for `/platform`, `/pricing` and `/live`.

**Fix:** pre-render at build time. With Vite this is a small addition — `vite-plugin-ssg`, `vite-prerender-plugin`, or a post-build script that boots each route and writes static HTML. Seven routes, all static content, no data fetching: this is the easy version of the problem. It also fixes finding 3 for free.

**✅ Resolution.** Build-time prerendering, with no new runtime dependency:

1. `seo.js` was split — a pure `getSeoData(pathname)` now returns the metadata, and both the client `applySeo()` and the prerenderer consume it, so rendered and prerendered heads cannot drift.
2. [src/entry-server.jsx](src/entry-server.jsx) renders `<App>` through `StaticRouter`. The components were already SSR-safe: everything touching `window` does so in `useEffect`, and the two render-time helpers in `motion.jsx` already guard on `typeof window !== 'undefined'`.
3. [scripts/prerender.mjs](scripts/prerender.mjs) builds each route, strips the generic tags from the `index.html` template (so pages carry exactly one title/canonical/OG/schema set, not two competing ones), and writes `dist/<route>/index.html`.
4. `main.jsx` now calls `hydrateRoot` when the container already has markup, falling back to `createRoot` for the dev server.

Build output:

```
Prerendered 7 routes + 404.html
  /          -> index.html            23.8 kB      /live      -> live/index.html      27.6 kB
  /platform  -> platform/index.html   19.9 kB      /contact   -> contact/index.html   11.7 kB
  /pricing   -> pricing/index.html    17.1 kB      /privacy   -> privacy/index.html    9.2 kB
                                                   /terms     -> terms/index.html      8.7 kB
```

Each route now serves **its own** title, description, canonical, OG/Twitter tags and JSON-LD in the raw HTML, with 4,000–7,400 characters of real body copy. Verified exactly one of each head tag per document, and that hydration produces **no console output on any route** — no mismatch warnings. Client-side navigation still updates title and canonical correctly.

> ⚠️ **This uncovered a second problem.** `vite preview` served the homepage for *every* route, which at first looked like the prerendering had failed. It hadn't — the files on disk were correct — but it exposed that the **SPA-fallback hosting configs would have silently undone this fix in production**. `vercel.json` rewrote `/(.*)` to `/index.html`, and `_redirects` had `/* /index.html 200`. Both have been rewritten (see finding 3). A purpose-built [scripts/serve-dist.mjs](scripts/serve-dist.mjs) now reproduces production hosting semantics locally, because `vite preview` structurally cannot verify this.

### 2b. Prerendering made an existing risk sharper — handled

Real content now ships in the HTML, including `.reveal` blocks that start at `opacity: 0` and are revealed by an IntersectionObserver. If scripting never runs, that copy would be permanently invisible — worse than having shipped nothing. Two guards were added:

- A `<noscript>` block in `index.html` forcing `.reveal { opacity: 1 }`, which propagates into all 8 prerendered documents.
- A mount-time check in `Reveal.jsx`: anything already at or above the fold is revealed immediately instead of waiting for an intersection that has already happened.

During testing a sweep reported only 5 of 17 elements revealed on `/pricing`, which looked like a real bug. It was my test scrolling 60% of a viewport every 110 ms without waiting for a rendering update — the observer was being outrun by the harness, not by a browser. A frame-respecting scroll reveals **17 of 17**. The guards above stay in regardless, because the failure mode is severe and they cost nothing.

### 3. 404s return HTTP 200 with `index, follow` — ✅ FIXED

The SPA fallback in [scripts/prepare-sites-build.mjs](scripts/prepare-sites-build.mjs) refetches `/index.html` and returns that response verbatim — status **200**. `vercel.json` and `public/_redirects` do the same. So `/nonexistent-page` returns `200 OK`, and the HTML it returns statically declares `<meta name="robots" content="index, follow">`.

`seo.js` does set `noindex, nofollow` for unknown paths — but again, only after JS runs. A non-rendering crawler sees an indexable 200 page carrying the homepage title. This is a textbook soft-404 and it lets crawlers accumulate junk URLs against your domain.

**Fix:** serve genuine 404s. In the worker, return the fallback with an explicit status:

```js
const res = await env.ASSETS.fetch(new Request(url, request));
return new Response(res.body, { status: 404, headers: res.headers });
```

Better still, pre-render a real `404.html` (which the pre-render step in finding 2 gives you) and have the host serve it with a 404 status.

**✅ Resolution.** A real `404.html` is prerendered (it carries `noindex, nofollow`, since `getSeoData` returns that for any unknown path), and **all three** hosting configs were corrected — the catch-all SPA fallbacks were the actual cause, and leaving any one of them would have kept soft 404s alive in production:

| Config | Was | Now |
|---|---|---|
| [vercel.json](vercel.json) | `rewrites: /(.*) → /index.html` | Rewrite **removed**; `cleanUrls: true`. Vercel serves the prerendered directory index, then its own 404 handling for `404.html`. The catch-all rewrite would have forced 200 on every unknown path. |
| [public/_redirects](public/_redirects) | `/*  /index.html  200` | `/*  /404.html  404` |
| Cloudflare worker | rewrote everything to `/index.html`, returning its 200 | Explicit resolution: exact asset → `<path>/index.html` → `/404.html` with an explicit 404 status |

Every route is prerendered, so there is nothing legitimate left for an SPA fallback to catch — an unmatched path genuinely *is* a 404.

Verified end-to-end against production-like hosting:

```
/           200  canon=/           robots=index, follow
/platform   200  canon=/platform   robots=index, follow
/pricing    200  canon=/pricing    robots=index, follow
/live       200  canon=/live       robots=index, follow
/contact    200  canon=/contact    robots=index, follow
/privacy    200  canon=/privacy    robots=index, follow
/terms      200  canon=/terms      robots=index, follow
/nope       404  canon=/           robots=noindex, nofollow
```

### 6. Form inputs have no visible focus ring — ✅ FIXED

[src/index.css:810](src/index.css#L810):

```css
.field input:focus,
.field textarea:focus {
  outline: none;                 /* ← kills the global :focus-visible ring */
  border-color: var(--violet);
  background: var(--surface);
}
```

The global `:focus-visible { outline: 2px solid var(--accent); outline-offset: 3px; }` at line 103 is overridden here. What remains is a **1px border colour change** from grey to violet. That is the sole focus indicator on the contact form — the only conversion surface on the site. It fails WCAG 2.4.11 (Focus Appearance) on both the area and contrast criteria, and in practice a keyboard user tabbing the form will struggle to tell which field they are in.

**Fix:** keep the styling, restore the ring.

```css
.field input:focus-visible,
.field textarea:focus-visible {
  outline: 2px solid var(--accent);
  outline-offset: 2px;
}
```

**✅ Resolution.** Applied exactly as above. The `outline: none` is gone; the bare `:focus` rule keeps the subtle border/background treatment for pointer users, and a new `:focus-visible` rule restores the ring for keyboard users. Verified with a real click event (not programmatic `.focus()`, which doesn't exercise the same heuristic): `#cf-name` matches `:focus-visible` and computes `outline: solid 2px rgb(91, 93, 240)` with a 2px offset.

### 8b. Aspect-ratio safety note

Adding `width`/`height` required one supporting change: the global rule was `img, svg { max-width: 100%; display: block; }` with **no `height` declaration**. Attributes alone would have constrained width via `max-width` while the `height` attribute stayed fixed — distorting every image on the site. A global `img { height: auto; }` was added; the three rules that deliberately set an explicit height (`.live-shot__image img`, `.venue-card__visual img`, `.live-hero__window > img`) are more specific and still win.

Verified no distortion: comparing each image's file aspect ratio against its **untransformed layout box** (`offsetWidth/offsetHeight`, immune to the `rotate()` on the hero cards) shows every image within 0.02 of its true ratio.

### 8. No image has `width`/`height` — guaranteed layout shift — ✅ FIXED

All 8 homepage images lack both attributes. The browser cannot reserve space, so every image pops the layout as it decodes. Two of them (`venue-home`, `staff-orders`) are `loading="eager"` hero images, which puts this squarely in your CLS score and in the first thing a visitor experiences.

**Fix:** add intrinsic `width` and `height` to every `<img>`. CSS already controls the rendered size; the attributes only supply the aspect ratio. This is a pure win with no visual change.

**✅ Resolution.** Every `<img>` on the site now declares intrinsic dimensions. Screenshots get them from the generated manifest via `<Shot>` (finding 7); the three logo assets get them from a dimension table in [Logo.jsx](src/components/Logo.jsx), which matters because the header is the first thing painted and a logo that pops in shifts everything below it.

See the aspect-ratio note in 8b above — the accompanying `img { height: auto }` rule is what makes this safe.

### 9. `aria-live="polite"` wraps 2,691 characters on `/live` — ✅ FIXED

[src/pages/Live.jsx:499](src/pages/Live.jsx#L499) puts `aria-live="polite"` on `#venue-project-details`, the container for the *entire* selected project — every section, heading, caption and stat. Measured content length: **2,691 characters**.

Switching venue re-renders that whole subtree, so a screen reader announces all 2,691 characters in one uninterruptible burst. Live regions are for short, incidental status updates. This is a hostile experience for exactly the users the rest of the site treats carefully.

**Fix:** remove `aria-live` from the container. Instead, move focus to the newly-rendered project heading (give it `tabIndex={-1}` and `.focus()` on change), which is the correct pattern for a user-initiated content swap. If you want an announcement, add a separate visually-hidden `aria-live="polite"` node containing only `"Now viewing {venue.name}"`.

**✅ Resolution.** Implemented as described. `aria-live` is off the container; the container takes `tabIndex={-1}` and receives focus on venue change via `focus({ preventScroll: true })`, guarded by an `isFirstRender` ref so arriving at the page doesn't yank focus out of the header. ### 13. No security headers configured anywhere — ✅ FIXED

`vercel.json` contains only a rewrite rule. `.openai/hosting.json` contains only a project ID. There is no `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy`, or `Permissions-Policy` — and no `Cache-Control` tuning, so hashed assets in `/assets/` are not being marked immutable.

This is not exploitable today (the site takes no user input beyond a form POST to a third party), but it is table stakes, it is what any prospect's IT-literate friend will check, and it is free:

```json
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }],
  "headers": [
    {
      "source": "/(.*)",
      "headers": [
        { "key": "Strict-Transport-Security", "value": "max-age=63072000; includeSubDomains; preload" },
        { "key": "X-Content-Type-Options", "value": "nosniff" },
        { "key": "Referrer-Policy", "value": "strict-origin-when-cross-origin" },
        { "key": "Permissions-Policy", "value": "camera=(), microphone=(), geolocation=(), interest-cohort=()" }
      ]
    },
    {
      "source": "/assets/(.*)",
      "headers": [{ "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }]
    }
  ]
}
```

Add a CSP once analytics is chosen, so the policy is written against the final script set rather than immediately needing amendment.

**✅ Resolution.** All of the above applied to [vercel.json](vercel.json), plus `X-Frame-Options: SAMEORIGIN` and a 7-day `Cache-Control` for `/live/` screenshots.

A CSP **was** included after all, rather than deferred — the site's full network surface is knowable from source, so the policy could be written precisely:

```
default-src 'self'; base-uri 'self'; object-src 'none'; frame-ancestors 'self';
img-src 'self' data:; font-src 'self' https://fonts.gstatic.com;
style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
script-src 'self'; connect-src 'self' https://formspree.io; form-action 'self'
```

`fonts.googleapis.com` / `fonts.gstatic.com` cover the Instrument Sans link in `index.html`; `connect-src https://formspree.io` covers the contact form's `fetch`; `style-src 'unsafe-inline'` is needed for Vite's injected styles. The inline JSON-LD is `type="application/ld+json"`, a data block rather than executable script, so `script-src 'self'` does not affect it.

> ⚠️ **Two things to know.** First, these headers only apply on Vercel — `public/_redirects` and `.openai/hosting.json` have no equivalent, so a deploy to a different host gets none of this. Second, the CSP could not be verified locally (the Vite dev server does not read `vercel.json`). **Confirm it on a preview deploy before promoting to production** — check that fonts render, the contact form submits, and the console shows no CSP violations. If analytics is added later, its domains must be added to `script-src` and `connect-src`.

### 17. The decorative scroll thread renders at DPR 1 on retina screens

[ScrollThread.jsx:245](src/components/ScrollThread.jsx#L245) caps the backing store: `Math.min(window.devicePixelRatio || 1, 1)`. Measured on a DPR 2 device, the canvas is 390×7810 CSS px backed 1:1 — so the thread is drawn at **half the display's resolution** and will look visibly soft on every modern phone and laptop. The comment explains this was a deliberate performance trade, and the dirty-rect repaint optimisation around it is good work. But the result is that a prominent brand flourish is the blurriest element on the page, on the devices most people will use.

The canvas is also ~11.6 MB of pixel buffer on the mobile homepage (390 × 7810 × 4 bytes), which is a real memory cost on older phones.

**Fix:** allow DPR up to 2 but reduce the canvas height — split into a windowed canvas that only covers the viewport plus overscan, positioned `fixed`, rather than one canvas spanning the full 7810px document. That gets full sharpness at roughly a tenth of the memory.

### 18. The honeypot can silently discard a genuine enquiry — ✅ FIXED

if (values.website) {

## What a paying customer actually experiences

Walking the site as a venue owner who was handed a card at their door:

**What works.** The hero states the offer plainly and the two CTAs are unambiguous. Real product screenshots appear immediately rather than abstract illustration — this is the site's single strongest choice, and it separates CentralPass from every template-studio competitor. The live Caffe Primo Firle link is genuine, external and verifiable, which is worth more than any amount of copy. The Pricing page's five-phase breakdown is honest and unusually clear about *what you are buying* even without a number. Marking works-in-progress as blurred rather than faking finished work reads as integrity, and an owner will notice that. The "not on the list? ask us to build it" thread running through Platform, Pricing and Contact is a real differentiator against fixed-tier SaaS.

**Where they stall.** The moment of hesitation is predictable and it is the same three questions:

1. *"Who is this?"* — no name, no face, no ABN, no team. A bespoke build is a months-long relationship with a person, and the site never introduces one.
2. *"Has anyone else done this and been happy?"* — one live venue, no quote, no outcome. The stats describe how much was built, never what improved. "100+ menu items" tells an owner about *your* effort, not *their* result.
3. *"What is this going to cost, roughly?"* — the honest refusal to quote is defensible but it means a cautious owner has to spend a phone call to find out whether they're even in the right price bracket. Many won't.

Then, more quietly: *"What happens if it breaks during service?"* The site never raises reliability, support hours, backups or failure modes — and the buyer is being asked to put their ordering, their kitchen and their staff clock-ins on it. Silence here doesn't read as reassurance; it reads as not-yet-thought-about.

**The mobile reality.** They will open this on a phone. There, they will also encounter: a third of the platform modules off-screen with no hint they exist (10), the value-proposition paragraph at under a third of the required contrast (5), full desktop-resolution screenshots on mobile data (7), and images that shift the layout as they load (8).

**And if you send them a link.** Because of finding 2, sharing `/live` in a follow-up text renders as the generic homepage card. The single most persuasive page you have does not survive being shared — which, for a door-knocking pipeline where the follow-up message *is* the funnel, is the most commercially expensive defect in this document.
